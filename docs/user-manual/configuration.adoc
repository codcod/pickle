= Configuration — `pickle.toml`

`pickle.toml` lives at the overarching-project root and is *tool-managed*.
Existing files are rewritten only in the cases below:

* *`project add|remove`* re-render the whole file to a canonical layout. That
  re-render *does not preserve comments* — this is the one case where
  hand-written notes are lost.
* *`upgrade`* rewrites only the `payload_version` line. The first time a
  project upgrades on a binary that knows the key, it also inserts a `layout` line
  when one is not already present (<<install-layout>>). Comments, blank
  lines, key order and every other line's spacing survive; the
  `payload_version` line comes back normalised to `payload_version = "value"`,
  with any inline comment after the value kept — so that one line's alignment
  and quoting style are not preserved. The line editor tracks multi-line
  strings and array nesting as it scans, so a quoted `"payload_version"` key
  and a table-looking or key-looking line inside an unrelated multi-line
  string are read correctly wherever they sit in the file — position is not
  what decides it. Two shapes are beyond a line-based edit by design:
  `payload_version`'s own value being a multi-line string or an array —
  pickle never writes either, so it only happens to a hand-edited file — and
  a file that does not parse to begin with (for example, a duplicated key).
  And because the editor is a bounded scanner rather than a full TOML parser,
  a sufficiently exotic file can still defeat it (an inline table `{ … }`
  written across several lines, say). None of that can cost you content for
  the `payload_version` stamp: the result is always parsed and compared
  against the original before anything is written, so whenever the editor
  cannot do the job that stamp *refuses and changes nothing* and tells you to
  set the version by hand, naming the offending line whenever it knows which
  one it is. The `layout` back-fill is narrower — it only ever inserts the
  line, never rewrites an existing one — and confirms the insert by re-reading
  the file afterward rather than refusing beforehand.
* *`install`* writes `pickle.toml` only when it does not yet exist; on an
  existing file it reports `= pickle.toml (exists)` and leaves it alone.

Hand-edits are always preserved on load.

== The keys

*Overarching:*

* `payload_version` — the payload pinned into this project (stamped by
  install/upgrade).
* `layout` — `"umbrella"` or `"in-tree"` (<<install-layout>>), recorded by
  `install` and back-filled by `upgrade` when absent. A config with neither
  the key nor a child at `.` is `"umbrella"`; a config with no key but a
  child at `.` is `"in-tree"` — the pre-`layout` compatibility inference,
  never a substitute for the recorded value once it exists.
* `flow` — the flow this project runs, read by `pickle flow show|list`
  (<<cmd-flow>>); defaults to `{flow}` when unset, currently the only legal
  value (`Config.Validate()` rejects any other).
* `review_addendum` (optional) — a project-wide addendum layered *on top of — never
  instead of* — the skill's review protocol, applied before any per-child addendum; see
  <<lifecycle>> for how it's structured and when to add one.
* `[commit]` table — `overarching_auto`, `child_publish_gated`. Both default
  to *`true`* when the key or the whole table is absent. This is the cautious
  reading, and what `install` writes: a child is not pushed without your
  approval. Set either to `false` explicitly to opt out. The wording rendered
  into `AGENTS.md` follows whichever way they are set (see <<cmd-upgrade>>).

*Per child — the `\[[project]]` array* (one entry per connected child):

* `name`, `path` (relative to the root);
* `build` / `test` / `lint` / optional `docs` — the child's own commands, used
  by the agent when implementing and reviewing tickets that target it (this
  repository, for example, registers `docs = "just docs-check"` to validate
  this manual);
* `ticket_prefix` (default `T`) — the per-child id prefix (`<PREFIX>-NNN`);
* `branch_prefix` (default `feat/`);
* `wip_in_development` / `wip_in_review` (default 1);
* optional per-child `review_addendum` — that child's own addendum, applied after the
  overarching one, if any; same guidance, <<lifecycle>>.
* `rick` (default `false`) — opts this child into rick interop: pickle shells out to
  `rick status --json` for it, to learn which https://gitlab.com[rick/ai-sdlc] artifacts exist
  under its `docs/specs/` tree and which are still awaiting approval. Off by default and never
  auto-detected. A child that has never heard of rick sees no behaviour change at all. A child
  that turns it on but has no `rick` on `PATH` (or hits any other failure) fails open: no error,
  no warning, just nothing to show. `pickle doctor -v` reports the result either way.
* `specs_root` (default `"docs/specs"`) — the child-relative directory rick's artifacts live
  under; only meaningful once `rick` is `true`.

The shipped {flow} skill (`{skill-dir}/`) states only the
flow's *defaults* for the ticket-id prefix, the branch prefix, the WIP limits
and the commit policy; the project's actual configuration can differ. For the
authoritative render of what is actually configured, read the `AGENTS.md` marker block.
After changing `ticket_prefix`, `branch_prefix`,
`wip_in_development`/`wip_in_review` or `[commit]`, re-run `pickle upgrade` (or
`pickle project add`, which re-renders it directly) and read the marker block
— not the skill — for this project's real values. `review_addendum` is not part of that
render — the review mechanism picks it up regardless, but nothing else points a reader at it
unless the project names it by hand in `AGENTS.md` (<<lifecycle>>).

== Parsing

TOML is decoded with
https://github.com/BurntSushi/toml[`github.com/BurntSushi/toml`] — a
*build-time* dependency compiled into the static binary; nothing is fetched at
runtime.
