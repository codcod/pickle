[#installation]
= Installation

[NOTE]
====
*Two different "installs."* This page installs the *`pickle` binary* on your
machine. The `pickle install` _command_ (see <<cmd-install>>) is a separate
step you run *inside a project* to lay down the flow (skill, board, markers).
====

== Homebrew

Via the tap:

[source,sh]
----
brew install codcod/tap/pickle
----

== Debian and Ubuntu (apt)

Every final release (not prereleases) is published to the Cloudsmith apt
repository `codcod/pickle-cli`.
The package itself is named `pickle`. Add the repository once, and `apt upgrade`
picks up each new version:

[source,sh]
----
curl -1sLf 'https://dl.cloudsmith.io/public/codcod/pickle-cli/setup.deb.sh' | sudo -E bash
sudo apt install pickle
----

If the setup script does not recognise your release (this can happen for a
distribution newer than the script), add the source by hand instead:

[source,sh]
----
curl -1sLf https://dl.cloudsmith.io/public/codcod/pickle-cli/gpg.key \
  | sudo gpg --dearmor --yes --output /usr/share/keyrings/pickle-cli.gpg
. /etc/os-release
echo "deb [signed-by=/usr/share/keyrings/pickle-cli.gpg] https://dl.cloudsmith.io/public/codcod/pickle-cli/deb/$ID $VERSION_CODENAME main" \
  | sudo tee /etc/apt/sources.list.d/pickle-cli.list
sudo apt update && sudo apt install pickle
----

The path uses your distribution's own `$ID` and `$VERSION_CODENAME` (for
example `ubuntu noble`). The package is uploaded as `any-distro`, but that is
not a valid path in the source line. `--yes` lets the commands be re-run, for
example after a key change, without gpg stopping to ask about overwriting.

Offline, download `pickle_<version>_amd64.deb` (or `_arm64`) from the
https://github.com/codcod/pickle/releases/latest[latest release], together with
`checksums.txt`, then check and install it:

[source,sh]
----
sha256sum --ignore-missing -c checksums.txt
sudo dpkg -i pickle_<version>_amd64.deb
----

A package installed this way does not update itself.

== Windows

Download `pickle_<version>_windows_amd64.zip` (or `_arm64`) from the
https://github.com/codcod/pickle/releases/latest[latest release], unzip it,
and put `pickle.exe` on your `PATH`.

`pickle install` links `.claude/skills/brine` to the skill directory. Windows
only allows that with Developer Mode on (or as an administrator). Without it,
pickle writes a copy of the skill there instead, and `pickle upgrade` keeps
the copy current. `pickle install --claude-symlink` likewise falls back to the
default `CLAUDE.md`, a marker block holding the `@AGENTS.md` import.

If the project you clone already commits those paths as symlinks, turn on
Developer Mode and run `git config --global core.symlinks true` _before_
cloning. Otherwise git checks each link out as a small placeholder file
holding the link's target. `pickle doctor` reports both placeholders.
`pickle upgrade` replaces the `.claude/skills/brine` one with a copy, which git
then shows as changed: don't commit that. A `CLAUDE.md` placeholder is never
written to.

== go install

Go 1.26+, any platform:

[source,sh]
----
go install github.com/codcod/pickle@latest
----

NOTE: `brew install` / `go install` work once the GitHub repo and tap exist, and
once a release tag is cut — see pickle's own `RELEASING.md` in the repository.
(For the `RELEASING.md` convention as it applies to *your* project, see
<<releasing>>.)

== From source

Requires Go 1.26+ and (optionally) https://github.com/casey/just[`just`].
Releasing also needs https://goreleaser.com[`goreleaser`]
(`brew install goreleaser`).

[source,sh]
----
git clone https://github.com/codcod/pickle
cd pickle
just build         # → ./pickle   (or: go build -o pickle .)
just test          # go test ./...
just lint          # go vet + gofmt check
just dist-check    # validate .goreleaser.yaml
just dist-snapshot # local cross-compiled build into ./dist (no publish)
./pickle version
----

Cutting an actual release is tag-driven and documented in the repository's own
`RELEASING.md` — pickle's, not yours. <<releasing>> covers the convention for
your project.

== Then, inside any project

[source,sh]
----
pickle install        # lay down brine — see the CLI reference
pickle hooks install  # optional: guard ticket bookkeeping (once per clone)
pickle version
----

`pickle hooks install` arms two guards. A `pre-commit` guard refuses ticket
and board bookkeeping staged on a feature branch, and a `pre-push` guard
refuses a push whose destination is such a branch when the range against the
remote base still carries the same bookkeeping. Together they enforce the one flow rule nothing
else can: at both commit time and publish time. Hooks live in `.git/` and are
never cloned or pushed, so run this
once in **each** clone you work from, including a fresh clone of a project
that already uses it. See <<cmd-hooks>>.

Both guards run whatever `pickle` is first on your `PATH`, not necessarily the
binary that just ran `hooks install` — if you installed from a freshly built
binary while `PATH` still resolves an older release (Homebrew lag, a second
clone, `go install` alongside a packaged copy), `pickle doctor` will tell you
the guards are inert instead of reporting them as healthy
(<<hooks-version-skew,version skew>>).

Continue with <<your-first-project>>.
