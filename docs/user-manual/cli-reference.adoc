[#cli-reference]
= Commands

Every command, its synopsis, and its contract. {product} operates on the
current working directory (finding `pickle.toml` upward from it); nothing is
ever written to `~/` or outside the project root.

Commands that change an existing ticket tree (`ticket new`, `ticket move`,
`board sync`, `project add`, `project remove`) first take an exclusive lock,
so two `pickle` commands — or a `pickle` command and `pickle serve` — cannot
race each other. `pickle serve`, `pickle board state --json`
(<<cmd-board-state>>) and `pickle board decisions`
(<<cmd-board-decisions>>) take only a shared read lock, so any number of
dashboards or read-projection calls can run at once alongside the CLI.
`install` is the exception: it creates the tree rather than changing one, so
there is nothing for a concurrent reader to observe half-done. The
lock file lives at `.git/pickle-tree.lock` (or, outside a git checkout, a
fixed path under your OS's temp directory) and is created automatically the
first time a write command runs — it is empty, safe to ignore, and never
needs deleting by hand. If a command refuses with a message naming this lock
file, another `pickle` command or `pickle serve` is already running against
the same tree. Wait for it to finish, then try again.

== Overview

[cols="2,3"]
|===
| Command | What it does

| `pickle install [--agent …]`
| Scaffold `tickets/` + install the skill + inject markers + write
  `pickle.toml` + register the first child-project.

| `pickle project add\|list\|remove`
| Manage connected child-projects.

| `pickle flow show\|list`
| Print, or list, the configured flow name.

| `pickle upgrade`
| Refresh the installed skill payload + marker block to the binary's version.

| `pickle doctor`
| Verify install integrity.

| `pickle uninstall [--dry-run]`
| Remove skill/symlinks/markers; keep `tickets/` + `pickle.toml`.

| `pickle hooks install\|uninstall\|status\|run`
| Manage the `pre-commit` and `pre-push` guards that refuse ticket bookkeeping
  staged on, or pushed from, a feature branch.

| `pickle ticket new "<title>" --project <name>`
| Allocate `T-NNN`, scaffold the ticket, regenerate the board.

| `pickle ticket move T-NNN <status>`
| Move the file + append History + regenerate the board, atomically.

| `pickle board audit`
| Check every ticket invariant + board freshness.

| `pickle board sync`
| Regenerate the board from ticket state.

| `pickle board state --json`
| Print the whole ticket tree as one versioned JSON document.

| `pickle board decisions [--project …] [--status …] [--grep …] [--json]`
| Query every ticket's confirmed design decisions, in citable `<ID> decision <N>` form.

| `pickle changelog check [--since …] [--until …] [--changelog …] [--section …] [--show-excluded]`
| Report tickets that shipped since the last release but aren't named in the
  changelog. Read-only and advisory — always exits `0`.

| `pickle serve [--addr …]`
| Serve a read-only browser view of the board, the tickets, and their history.

| `pickle scaffold docs [--project-name …] [--force] [--dry-run]`
| Write a minimal AsciiDoc docs skeleton, best-effort `snowball init`, additive
  justfile recipes and a standalone release-attach GitHub Action. Entirely
  separate from `pickle install` — unrelated to {flow}.

| `pickle version` · `pickle help`
| Print the version / the usage summary.
|===

[#cmd-install]
== `pickle install`

----
pickle install [--in-tree] [--project <name>] [--path <path>] [--build/--test/--lint/--docs <cmd>]
               [--agent claude,opencode,pi] [--claude-symlink] [--hooks]
----

Run once in a project to lay down the flow. It:

* copies the embedded skill payload into `{skill-dir}/` (real
  files) — including `resources/docs-readability.prompt.md`, the shared system
  prompt for the optional docs-readability reviewer (review protocol Step 4b);
* scaffolds `tickets/` (the seven ordered status dirs, each with a
  `.gitkeep`), renders a fresh `tickets/BOARD.md` (a generated file — see
  <<cmd-board-sync>>), scaffolds `tickets/NOTES.md` for hand-written planning
  notes, and writes a short `tickets/README.md` pointer;
* injects an idempotent `<!-- pickle:begin -->`…`<!-- pickle:end -->` marker
  block into `AGENTS.md`;
* writes `pickle.toml`, recording the *layout* and registering a first
  child-project accordingly (see <<install-layout>> below);
* wires up each agent named in `--agent` (see below);
* with `--hooks`, also installs the bookkeeping guard hooks (`pre-commit` and
  `pre-push`), exactly as <<cmd-hooks>> does. They are opt-in because they
  write outside the install root (into `.git/`), and a failure there is
  reported as a warning: the install itself is already complete and correct.

[#install-layout]
=== Layout: umbrella (default) or in-tree

Every project resolves to one of two layouts, recorded as `layout` in
`pickle.toml` — never guessed, because only the human running `install` knows
which one is intended:

[cols="1,3"]
|===
| Layout | What it means

| `umbrella` (default)
| The overarching project and its children are separate git repositories.
  Plain `pickle install`, with neither `--in-tree` nor `--path`, writes
  `layout = "umbrella"` and registers *no child yet* — add the first one
  afterwards with `pickle project add` (<<cmd-project>>). Passing `--path
  <dir>` (a directory other than `.`) registers that first child immediately,
  still under the umbrella layout.

| `in-tree` (`--in-tree`)
| The sole child and the overarching project are the *same* repository: pass
  `--in-tree` to register it at `.` and record `layout = "in-tree"`. A bare
  `--path .` without `--in-tree` is refused — spell out the flag, since it is
  the one place this choice is made explicit rather than inferred.
|===

*Why the choice matters.* Ticket status is a directory name inside
`tickets/`, and different git branches can disagree about where a file lives.
Under the umbrella layout that cannot happen: the board is outside every
child's repository, so a child's feature branches cannot fork it.

Under the in-tree layout, they can. A feature branch cut before the latest
bookkeeping commit on the base branch carries a stale copy of `tickets/`, and
every command that reads it (including <<cmd-serve>>) reports that stale copy
without otherwise saying so. In-tree is still a reasonable choice — it makes
tickets visible to anyone who clones the code — but it is a trade-off, not a
free default. That is why `install` insists on hearing the choice from you
instead of inferring it from the directory you happen to be standing in.

`pickle doctor` (<<cmd-doctor>>) checks that the recorded layout and the
registered children actually agree, and `pickle upgrade` (<<cmd-upgrade>>)
back-fills the key on a project installed before this existed.

=== `--agent` — which coding agents to wire up

`--agent` takes a comma-separated set of `claude`, `opencode`, `pi` (default:
`claude`). There is *no autodetection* — the set is exactly what you name.
Every agent reads the same `AGENTS.md` + `{skill-dir}/` core;
the per-agent artifacts are:

[cols="1,3,1"]
|===
| Agent | Artifacts | Ownership

| `claude`
| `.claude/skills/brine` symlink + `CLAUDE.md` marker block
  (`--claude-symlink` makes `CLAUDE.md` a symlink to `AGENTS.md` instead)
| pickle-owned

| `opencode`
| `opencode.jsonc` — the `docs-readability` reviewer subagent + declarative
  bash guardrails (explicit-pathspec staging, publish gate). OpenCode picks up
  `AGENTS.md` and the skill natively; this config is the only
  opencode-specific piece
| *user-owned once written* (see below)

| `pi`
| `.pi/extensions/pickle-guardrails.ts` (the same rules as a Pi `tool_call`
  gate) + `.pi/extensions/docs-readability.ts` (a `docs_readability` tool +
  `/docs-readability` command)
| pickle-owned
|===

`--no-claude` is *deprecated*: it still works (drops `claude` from the set,
with a warning) — use `--agent` instead.

*`opencode.jsonc` policy.* pickle writes it whole *only if absent* and never
parses or merges JSONC: if the file already exists it is left byte-for-byte
untouched and the template is printed for you to merge by hand. From then on
the file is yours — `upgrade` never touches it, and `uninstall` removes it
only while it is still byte-identical to the shipped template.

*The docs-readability reviewer* is a read-only, suggestions-only AI
reviewer for the `.adoc`/`.md` files a ticket changed (review protocol
*Step 4b* — optional, never blocking). Both scaffolds default to
`github-copilot/gpt-5.4` (one-time GitHub Copilot login; adjust with
`opencode models github-copilot`, or `DOCS_READABILITY_PROVIDER`/
`DOCS_READABILITY_MODEL` for the pi extension).
Sessions in other agents (zed, Claude Code, …) can reach the opencode reviewer
by shelling out:
`opencode run --agent docs-readability --file <changed.md> "…"` — or record a
conscious skip.

*Per-project* (never writes to `~/` or outside the root), *idempotent, and
safe to re-run*: the payload and marker block are refreshed in place while
instance data (`BOARD.md`, `NOTES.md`, tickets, `pickle.toml`) is preserved
once present. After installing, a post-install `board audit` self-check must
pass. An existing `{skill-dir}` *symlink* (a dev/self-host
link) is left untouched.

[#cmd-project]
== `pickle project add | list | remove`

----
pickle project add <name> <path>
pickle project list
pickle project remove <name>
----

Manages the registry of connected child-projects in `pickle.toml` (see
<<multi-project>>):

* `add` registers another child — its name becomes a legal `project:`
  frontmatter value, and per-child keys (commands, branch prefix, WIP limits)
  can then be set in `pickle.toml`. Pass `--ticket-prefix <PREFIX>` to give the
  child its own ticket-id prefix (an uppercase letter plus up to seven more
  uppercase letters/digits, e.g. `RICK`); its tickets are then numbered
  independently as `RICK-001`, `RICK-002`, …. The prefix defaults to `T`, and
  any number of children may share that default (the one legacy global `T`
  namespace); two children may not share the same _explicit_ prefix. `board
  audit` checks that each ticket's id prefix matches its child's configured
  prefix — so changing a populated child's prefix reports every not-yet-renamed
  ticket until you renumber them. The other per-child keys can also be set
  directly as `add` flags instead of hand-editing `pickle.toml` afterwards:
  `--build <cmd>`, `--test <cmd>`, `--lint <cmd>`, `--docs <cmd>` (the child's
  own commands), `--branch-prefix <prefix>` (default `feat/`), and
  `--wip-dev <n>` / `--wip-review <n>` (default `1` each, the per-child WIP
  limits).
* `list` prints the registered children (including each child's `PREFIX`).
* `remove` unregisters a child — *refused while the child has live tickets*,
  so a board can never reference an unknown target.

`add` and `remove` re-render `pickle.toml` to a canonical layout; hand-written
comments in the file do not survive that re-render (see <<configuration>>). Both
also re-inject the `AGENTS.md`/`CLAUDE.md` marker block immediately, the same
way `install` and `upgrade` do (see below) — so the agent instructions never
describe a registry state that no longer matches `pickle.toml`. Both also
*regenerate `tickets/BOARD.md`* immediately, printing `+ tickets/BOARD.md`. The
registered-child list is itself a board-rendering input: every status heading
gains or loses a per-child `### <child>` section and WIP line. Without this,
the very next `pickle board audit` or `pickle upgrade` would report the board's
layout as stale for a registry change that just happened (<<cmd-board-audit>>).
A failed regeneration (a ticket file with a load problem) never fails the
registration, already saved by then — it prints a `note:` pointing at
`pickle board sync` instead.

When `<path>` is anything other than the repository root itself, `add` also
checks whether *this* repository would still stage that nested child whole —
that is, whether anything yet tells git to leave it alone: a `.gitignore`
entry, or an index entry for a deliberate submodule/gitlink. If nothing does,
`add` prints a `note:` line naming the entry to add. `pickle doctor` (below)
repeats the same check on every run, so a child that drifts into this state
later (an entry deleted, or a child registered before the check existed) is
still caught. pickle never writes to `.gitignore` itself — see
<<project-structure>>.

[#cmd-flow]
== `pickle flow show | list`

----
pickle flow show
pickle flow list
----

Both read `pickle.toml` and take no arguments. `show` prints the project's configured
flow — the `flow` key (default `{flow}` when unset, <<configuration>>). `list` prints
every legal flow name, one per line. Today that is exactly one name, `{flow}`, because
`Config.Validate()` rejects any other value, so treat it as a fixed constant until a
second flow ships. Both fail the same way any other command does when `pickle.toml`
does not parse.

[#cmd-upgrade]
== `pickle upgrade`

----
pickle upgrade
----

Refreshes an existing install to the running binary's payload. It re-copies
the embedded skill payload into `{skill-dir}/` (removing files
that the new payload dropped), re-injects the `AGENTS.md` marker block, and
stamps `payload_version` in `pickle.toml`. It also back-fills `layout`
(<<install-layout>>) when the key is entirely absent — inferred the same way
`install` would have chosen it (a child registered at `.` infers `in-tree`,
otherwise `umbrella`) — so a project installed before the key existed gains it
on its next upgrade with no separate migration step. A `layout` that is
already present, of any value, is never touched: the recorded choice always
wins over the inference. Takes no flags and no arguments.

*It never reads or writes anything under `tickets/`* — your board and tickets
are instance data and are not upgrade's business. Only artifacts that already
exist are refreshed: `CLAUDE.md` is re-injected only if it is a regular file
(a `CLAUDE.md -> AGENTS.md` symlink is left alone), and the
`.claude/skills/brine` view is re-linked only if it is already there. A
self-host *symlinked* `{skill-dir}` is left untouched, never
followed and overwritten. The `payload_version` stamp **is** still updated in
that case whenever it actually differs (an already-current version is a no-op,
as below): `upgrade` refreshed everything else it owns — the marker block, the
pi scaffolds, the hook shim — so the stamp truthfully records that this tree
was last upgraded by this binary.

Idempotent: re-running at the current version still refreshes the payload and
marker block (so drift is corrected) and reports `already at <version>`
instead of failing. A post-upgrade `board audit` self-check must find *no
errors* — a warning (e.g. the board's generated layout being stale, see
<<cmd-board-audit>>) is printed but does not fail the upgrade.

Upgrade will not cost you hand-written content in `pickle.toml`: stamping a
new version rewrites *only* the `payload_version` line, and back-filling
`layout` inserts *only* that one new line — both leave every other line
alone. Stamping `payload_version` refuses outright, changing nothing, when it
cannot verify the edit is that narrow (see <<configuration>>); back-filling
`layout` inserts the line and then re-reads the file to confirm the key is
now there, erroring out if it is not — a check *after* the write rather than
a refusal *before* it, since `layout` is only ever inserted, never rewritten
in place. Two things it _does_ replace wholesale, by design:

* the `<!-- pickle:begin -->`…`<!-- pickle:end -->` region of
  `AGENTS.md`/`CLAUDE.md`. It is regenerated from `pickle.toml` by `install`,
  `upgrade` **and** `project add`/`remove` (<<cmd-project>>), so everything
  it states about your project comes back — the registered child names, each
  child's `build`/`test`/`lint`/`docs` commands, each child's
  `branch_prefix`, each child's `ticket_prefix`, each child's WIP limits, and
  the `[commit]` policy wording — but anything you wrote in there yourself
  does not. Keep notes *outside* the markers, where pickle never looks.
  Because that block is what an agent reads first, the `[commit]` keys decide
  whether it is told to hold a child-project back pending your approval or to
  push as the work needs.
* the skill directory `{skill-dir}/`, which is pickle-owned and
  re-copied in full. Do not keep hand-written files there (a self-host
  _symlink_ is left untouched).

Agent scaffolds follow the same probe-what-exists rule: the pickle-owned
`.pi/extensions/` files are refreshed *if present* (put customizations in
sibling extension files — `doctor` warns when a pickle-owned one drifts),
while `opencode.jsonc` is user-owned after creation and is *never* touched by
upgrade.

[IMPORTANT]
====
*Upgrading from before the skill directory was renamed to `brine` (T-074,
pre-1.0 breaking change):* `upgrade` first *sweeps away* the old
`.agents/skills/ticket-flow/` directory and the `.claude/skills/ticket-flow`
symlink, then refreshes `{skill-dir}/` as usual — there is no dual-name
period, and the swept paths are reported alongside the usual `created`/
`refreshed` lines. A legacy path that was itself a *self-host symlink* (a dev
checkout that had not yet renamed its own link) is *re-linked* at the new name
rather than deleted-and-recopied, so a self-hosting checkout is never turned
into an installed copy by the sweep. One thing the sweep does *not* fix: a
user-edited `opencode.jsonc` that still hardcodes
`.agents/skills/ticket-flow/resources/docs-readability.prompt.md` keeps that
stale path — `opencode.jsonc` is user-owned after creation and pickle never
parses or merges JSONC, so `upgrade` cannot repair it. Edit that one line to
`.agents/skills/brine/resources/docs-readability.prompt.md` by hand; a fresh
`opencode.jsonc` scaffolded by a current `install` already has it right.
====

[#cmd-doctor]
== `pickle doctor`

----
pickle doctor [--verbose|-v]
----

Verifies install integrity and exits non-zero on any error. It checks that:

* `pickle.toml` parses;
* the skill directory `{skill-dir}/` resolves to a directory
  and holds every payload file;
* the `.claude/skills/brine` symlink (when present) is a symlink and not
  broken;
* `AGENTS.md` (and a regular-file `CLAUDE.md`) carry the pickle marker block,
  and its content matches what `pickle.toml` renders today — a block that
  differs (e.g. hand-edited, or left behind by an install that predates a
  config change) is a *warning* pointing at `pickle upgrade` (customizations
  belong outside the markers, the same rule the agent-scaffold check below
  follows);
* pickle-owned agent scaffolds (`.pi/extensions/+*+.ts`) match the shipped
  version — a drifted file is a *warning* pointing at `pickle upgrade`
  (customizations belong in sibling files);
* *neither* pre-brine legacy path (T-074) is still present —
  `.agents/skills/ticket-flow/` or `.claude/skills/ticket-flow`. Unlike the
  payload-version check below, this is an *error*, not a warning: a tree
  carrying both names is serving a stale skill copy that some agents
  discover ahead of the current one, which `pickle upgrade` fixes by
  sweeping the old paths away (see the note under <<cmd-upgrade>>);
* the state of each hook (<<cmd-hooks>>: `pre-commit` and `pre-push`) is
  reported. Every hook is opt-in, so an absent hook is *not* a finding.
  `doctor` prints a line naming `pickle hooks install` instead — also the
  right next step after a fresh clone, since hooks are never cloned. Only a
  hook written by an *older*
  pickle is a *warning*, pointing at `pickle upgrade`; a hook pickle does not
  own is reported and left alone; when at least one hook is installed and
  current, whether the `pickle` first on `PATH` can actually run it is
  checked once — both hooks ship in the same binary, so this is a per-binary
  question, not a per-hook one — and reported as a *warning* naming the
  incapable binary's path and version when it cannot
  (<<hooks-version-skew,version skew>>);
* the recorded `layout` (<<install-layout>>) agrees with the registered
  children: `in-tree` requires *exactly one* child at `.`, and `umbrella`
  requires *none*. Either mismatch is an *error*, not a warning — a
  doctor-clean project must never carry a recorded layout its own config
  contradicts. The resolved layout is otherwise reported as a passed line
  under `--verbose`;
* each registered child's `path` is a git repository;
* a child registered at a path other than the repository root is either ignored by this
  repository's git or already tracked (a deliberate submodule/gitlink) —
  otherwise it is an ordinary stageable directory until someone remembers to
  add it to `.gitignore`, and that gap is a *warning* naming the child and the
  entry to add. A child at `.` (the single-repo default) is exempt — the child
  *is* the repo, nothing to ignore. `doctor` only ever reports this; it never
  writes to `.gitignore` itself;
* the installed `payload_version` matches the binary — a mismatch is a
  *warning*, and `doctor` first checks whether `upgrade` could actually
  stamp the new version (a check that writes nothing). If it could, the
  warning points at `pickle upgrade`; if `upgrade` would refuse (see
  <<configuration>>), the warning gives that reason and tells you to edit
  `payload_version` by hand instead — it never sends you to a command that
  cannot succeed. When `{skill-dir}` is a self-host symlink
  (a dev checkout pointing straight at the payload source, not an installed
  copy), this comparison is skipped entirely — there is nothing to
  compare — and the skip is reported as a passed line under `--verbose`,
  never a warning.

`--verbose` (`-v`) also lists the checks that passed.

[#cmd-uninstall]
== `pickle uninstall`

----
pickle uninstall [--dry-run|-n]
----

Detaches the flow from the project, leaving your work behind. It also sweeps
any pre-brine legacy paths (T-074, `.agents/skills/ticket-flow/`,
`.claude/skills/ticket-flow`) left by an older install, so a current binary
can still fully remove one — the swept paths are reported alongside the
usual removals below. Otherwise it removes
`{skill-dir}/`, the `.claude/skills/brine` symlink, the
`<!-- pickle:begin -->`…`<!-- pickle:end -->` marker block from
`AGENTS.md`/`CLAUDE.md` (a `CLAUDE.md` that is a symlink to `AGENTS.md` is
removed outright; a regular file keeps everything outside the markers, and the
file itself is never deleted), and the agent scaffolds: the pickle-owned
`.pi/extensions/` files go (pruning `.pi/` only when left empty — your own
extensions keep it alive), and `opencode.jsonc` goes *only* while still
byte-identical to the shipped template; one you have edited is yours and
stays. Pickle-owned hooks (<<cmd-hooks>>: `pre-commit` and `pre-push`) are
removed too; a hook pickle did not write is reported and left in place.

*`tickets/` and `pickle.toml` are both left intact* — the board, the tickets,
and the child-project registry are instance data, so a later `pickle install`
or `pickle upgrade` re-attaches cleanly to the same configuration.

`--dry-run` (`-n`) lists what would be removed and changes nothing.
Idempotent: on an already-clean tree it reports nothing removed rather than
failing. A self-host *symlinked* skill directory has only the link removed —
the tree it points at is never deleted.

[#cmd-hooks]
== `pickle hooks`

----
pickle hooks install [--force]
pickle hooks uninstall [--dry-run|-n]
pickle hooks status
pickle hooks run pre-commit
pickle hooks run pre-push
----

[NOTE]
====
**These guards protect one invariant, scoped to a repository, not to a layout:** ticket/board
bookkeeping must not ride along on a feature branch *of whichever repository holds `tickets/`*.
That is also the repository `hooks install` arms: it resolves its target upward to the directory
holding `pickle.toml`, so it is the board's repository that gets the shims no matter which
directory you run it from. A repository without a `tickets/` in it has nothing for the guard to
check, and a shim placed there by hand is a silent no-op regardless of layout.

Under the **in-tree layout** (<<install-layout>>) that repository is the child's own — the same
one the `feat/T-NNN-<slug>` branches are cut in — so the hazard is routine and the guards matter
on every commit.

Under the **umbrella layout**, every *child* repository is unaffected: `tickets/` lives in the
overarching project, a separate repository, so a commit in a child *cannot* stage a `tickets/`
path and a child's push *cannot* carry one — which is why `hooks install` never arms a child in
the first place, and why a shim copied into one by hand would never fire. But the **overarching**
repository is a different matter: it is the one that
holds `tickets/`, so if *it* is ever worked on from a feature branch (docs, `pickle.toml`,
planning prose in `tickets/NOTES.md`), the identical fold-or-drop hazard applies there too.
**Whether the guards catch it there depends on how that branch is named.** They recognise a
"feature branch" only by matching a registered child's `branch_prefix`, and under `umbrella` no
registered prefix describes the overarching project's own branches — so coverage there is a
coincidence of naming, not a guarantee, unlike the in-tree case above where a child's own prefix
names exactly the branches that carry the hazard. The base-branch discipline itself still holds
regardless; only the hooks' ability to catch a lapse in the overarching project does not.
"Umbrella" describes the *children*'s relationship to the board, not an exemption for the
repository that contains it, nor a guarantee that its own branches are covered.
====

Installs, inspects and runs two guards, both written by the same shared shim
machinery and sharing one marker version:

* **`pre-commit`** **refuses a commit that stages `tickets/` paths while a
  feature branch is checked out.**
* **`pre-push`** **refuses a push whose destination is a feature branch, when
  the range against the remote base still carries a `tickets/` path** — the
  same invariant a forge computes an MR diff from (`<remote>/<base>...<local>`,
  three dots). The branch is decided from the push's *destination* ref, not
  its source, so `git push origin HEAD:refs/heads/feat/T-NNN-x` and
  `git push origin main:refs/heads/feat/T-NNN-x` are both judged the same way
  a forge would judge the resulting merge request. It catches what
  `pre-commit` structurally cannot: bookkeeping committed correctly on the
  base branch that leaks into a feature branch's merge request because the
  remote base was behind when the branch was rebased onto it, or opened as an
  MR, before the base caught up.

Both exist because the flow puts code on a child's `feat/T-NNN-<slug>` branch
and ticket/board bookkeeping on the base branch. Bookkeeping that rides along
on a feature branch is folded into a single commit — or dropped — by a
squash-merge, after which `BOARD.md` indexes tickets whose recorded status
disagrees with where the files are. Each guard's rejection message names the
branch, the offending paths, and the way out. **Pushing the base branch itself
is never refused, whatever ref the push's source spells** — it is `pre-push`'s
single most important case to get right, since a project's bookkeeping
legitimately lands there by design.

`install` writes a short shim per hook, each calling back into
`pickle hooks run <name>` (`pre-push` additionally forwards its own
`<remote-name> [<remote-url>]` arguments and inherits stdin, exactly as git
invokes it), so the rule reads the live `pickle.toml` (each child's
`branch_prefix`) and cannot go stale the way a generated script with the
prefixes baked in would. Every shim is marked `# pickle:hook v3`, and that
marker is the whole of pickle's ownership claim for that file: a hook without
it is someone else's and is never modified, removed, or overwritten unless
you pass `--force`. To keep your own hook *and* a guard, chain it:

[source,sh]
----
pickle hooks run pre-commit || exit 1
----

[source,sh]
----
pickle hooks run pre-push "$@" || exit 1
----

The target directory is whatever `git rev-parse --git-path hooks` resolves to,
so an existing `core.hooksPath` (Husky, Lefthook, pre-commit.com) is honoured
and each shim lands where git will actually look for it. Pickle never sets
`core.hooksPath` itself — that setting is repo-global and would evict those
tools.

`pre-push` performs no network I/O (no `git fetch`): it resolves the remote's
base from the remote-tracking refs already on disk, in order —
`refs/remotes/<remote>/HEAD` (dereferenced), then `.../main`, then
`.../master` — and fails open with one stderr line if none resolves. A stale
remote-tracking ref can therefore only *widen* the diffed range, never narrow
it: the failure direction is a false refusal, never a false pass, and the
rejection message suggests `git fetch <remote> <base>` for exactly that case.

`uninstall` removes every pickle-owned hook it finds; `--dry-run` (`-n`)
reports what would go and changes nothing. `status` prints, per hook, the
state (absent, installed by pickle, stale, or foreign), the resolved path,
and — for an installed, current hook — whether the `pickle` first on your
`PATH` can actually run it (see *version skew*, below; checked once, not once
per hook).

[#hooks-version-skew]
=== Version skew: an installed shim is not the same thing as a working guard

The shim is a fixed file, but it calls back into *whatever* `pickle` is first
on `PATH` at commit time — and that can be a different, older binary than the
one that wrote the shim (a freshly built binary next to a lagging package
manager copy, a second clone, `go install` alongside Homebrew). `hooks
install`, `hooks status` and `doctor` (<<cmd-doctor>>) all probe for this —
running the same call the shim itself makes, in a directory with nothing in
it — and warn when the guard they just reported as "current" is one an older
`pickle` cannot actually run:

----
pickle hooks install: warning: the pickle on PATH cannot run the guard — it is
inert (0.2.2 at /opt/homebrew/bin/pickle)
  this binary is /usr/local/bin/pickle — put it first on PATH, or upgrade the
  pickle that is
----

This is a warning, never a failure: the shim on disk is correct regardless of
what happens to be first on `PATH` right now. Fix it by reordering `PATH` (put
the binary that ran `hooks install` first) or by upgrading whichever `pickle`
your package manager provides.

=== What the guards do and do not catch

[IMPORTANT]
====
**Hooks are per-clone.** They live in `.git/`, which git never clones or
pushes, so every clone of a project needs `pickle hooks install` once. This is
also why `pickle doctor` mentions an absent hook instead of assuming a project
that wants the guard already has it.
====

* **`git commit --no-verify` / `git push --no-verify` bypasses the matching
  guard**, deliberately — that is the escape hatch for the rare commit or push
  whose *product* is a file under `tickets/` (a change to the board
  renderer's fixtures, say).
* **`--amend` is checked against the index only (`pre-commit`).** The hook
  does run, but `git diff --cached` compares the index with `HEAD`, so
  amending a commit that *already* contains `tickets/` shows nothing to
  object to.
* **A merge, cherry-pick or revert in progress is passed through
  (`pre-commit`)**: those commits carry files you never staged by hand, and
  refusing them would leave you stuck mid-operation. A detached `HEAD` is
  passed through as well — there is no branch name to judge.
* **`pre-push` measures a range, not the stdin range git hands it.** On a new
  branch the remote side is all-zero; on a later push the stdin range is
  last-pushed…local, neither of which is what a forge diffs. It resolves
  `<remote>/<base>...<local>` itself instead, by the base-resolution order
  given above, and performs no network I/O to do it — a stale remote-tracking ref only ever widens the
  range, never narrows it.
* **It is best-effort and terminal-first.** Each shim finds `pickle` on
  `PATH`; GUI and IDE clients often commit or push with a minimal `PATH` that
  lacks `/opt/homebrew/bin` or `$GOPATH/bin`, and there the guard is silently
  skipped rather than blocking the operation.
* **An older `pickle` first on `PATH` degrades the same way, and now says
  so.** `hooks install`, `hooks status` and `doctor` each warn when the
  binary a shim will actually resolve cannot run the guard — see
  <<hooks-version-skew,version skew>>.
* **They are scoped to a repository, not a layout — and, within that repository, to a branch
  name.** A repository with no `tickets/` in it has nothing for the guard to catch, so installing
  it there is a harmless, permanent no-op — that is every **child** repository under the
  `umbrella` layout (<<install-layout>>), since `tickets/` lives in the overarching project
  instead. If a child repository's guard stays silent for the whole life of an umbrella project,
  that is correct, not a fault — do not read it as a broken hook or a missing install; check
  `layout` in `pickle.toml` first, and which repository you are asking about. It is *not* the
  overarching repository itself that is exempt: that one holds `tickets/`, so a feature branch cut
  there carries the same fold-or-drop hazard a child's would in-tree — but whether the guards
  *catch* it depends on that branch matching a registered child's `branch_prefix`, which names
  exactly the hazardous branches in-tree and names none of the overarching project's own branches
  under `umbrella`. There, the guard's silence on an unmatched branch name is not a signal either
  way — the discipline still applies, the hook just cannot see it.
* **Both fail open, always.** No `pickle` on `PATH`, no `pickle.toml`, an
  unparseable config, no git, an unresolvable base — each of those skips the
  check and allows the commit or push, with one line on stderr naming which
  case it was (`pickle: <hook> guard skipped (…)`) rather than staying
  silent. `pickle hooks run pre-commit` and `pickle hooks run pre-push` each
  exit `1` for a violation and *only* for a violation, `0` when the
  commit/push is fine or the guard could not run, and `2` for a bad
  invocation. That contract is what makes an older `pickle` first on your
  `PATH` harmless: it exits `2` on the unknown `hooks` verb, and each shim
  treats anything other than `1` as "no violation" instead of blocking every
  commit or push in the repository.
* **A foreign hook that chains the guard carries the same PATH-skew exposure, but is not
  probed.** Keeping your own `pre-commit`/`pre-push` and chaining in `pickle hooks run
  pre-commit || exit 1` (see the "chain it" examples above) resolves `pickle` from `PATH` exactly
  like the shim does, so an incapable `pickle` first on `PATH` degrades it the same way. `doctor`
  and `hooks status` only probe PATH capability for a hook they installed themselves
  (`KindOwned`); a foreign hook's line reports that it exists and is left alone, not whether
  whatever it chains can actually run, because presence alone does not say whether a foreign hook
  chains the guard at all. Verify PATH capability yourself (`pickle hooks run pre-commit` from the
  same shell a commit would use) if you chain the guard into your own hook.

[#cmd-ticket-new]
== `pickle ticket new`

----
pickle ticket new "<title>" --project <name> [--impact V --complexity V --cost V] [--spawned-by "T-NNN[,T-MMM]"] [--family T-NNN]
----

Allocates the next id for the target child's prefix — `<PREFIX>-NNN`, where
`<PREFIX>` is the child's `ticket_prefix` (default `T`) and `NNN` is
`max(existing ids sharing that prefix) + 1` — writes a clean, error-free
scaffold to `tickets/1-to-do/<PREFIX>-NNN-<slug>.md`
(filled frontmatter + the standard section skeleton; its `## Outcome`
placeholder is the one thing `board audit` warns about until you fill it in,
<<cmd-board-audit>>), and regenerates
`BOARD.md` (the row lands under the child's `### <child>` sub-group in the
TO DO section, in impact order). `--project` must name a registered child;
grades default to `medium`/`medium`/`M` and must be legal. The `<title>` may
not be empty, contain a line terminator, or exceed 120 runes — it is written
into the frontmatter and the heading, so a line break would corrupt both, and it
becomes part of a filename, so an unbounded one would fail late against the OS's
own limit instead of against a stated contract; a rejected invocation writes
nothing at all. "Line terminator" means all five: `LF`, `CR`, and the three
Unicode ones — `U+0085` (NEL), `U+2028` and `U+2029`. The last three change
nothing for pickle itself, which splits frontmatter on `LF` alone, but YAML 1.1
readers (Ruby Psych, PyYAML, and the static-site tooling built on them) treat
them as line breaks and would see a truncated title plus a phantom key. (A `|`
in a title is fine: board cells are sanitised one-way at render time.)
`--spawned-by` records *lineage* — the ticket(s) this one was born from
(a review finding, an audit, a split) — comma-separated, brackets optional,
defaulting to `[]`. It is provenance, not a dependency: it never gates pickup.
Each id is checked for *shape* (`T-NNN`) at creation, while whether it
*exists* is checked by `board audit` — a forward reference to a ticket not yet
filed is legal input. Repeated ids are de-duplicated. `--family <T-NNN>` sets a single
umbrella ticket id this one groups under for board ordering (same child only). It is
shape-checked at creation (`<PREFIX>-NNN`) and, like `--spawned-by`, never gates pickup —
whether the umbrella exists, is in the same child, and is not itself a family member is left
to `pickle board audit`. The agent fills the
Description prose afterwards; the full `TEMPLATE.md` (installed with the
skill) is the authoring guide.

Because it writes both the new ticket file and the regenerated `BOARD.md`, the
command prints a second, ready-to-paste `git add` line naming both — rules §0
requires bookkeeping commits to use explicit pathspecs, and a board update
named from memory is easy to leave out:

----
created T-099  (tickets/1-to-do/T-099-example.md)
  stage:   git add tickets/1-to-do/T-099-example.md tickets/BOARD.md
----

[#cmd-ticket-move]
== `pickle ticket move`

----
pickle ticket move <T-NNN> <status> [--reason "<why>"]
----

Moves a ticket through the flow as *one operation*: write the updated ticket
(with its dated `## History` transition line) to the target
`tickets/<status>/` dir, remove the old file, and regenerate `BOARD.md`. The
new file is written *before* the old one is removed, so a crash can never
leave a ticket whose History records a transition that did not happen.
`<status>` accepts the dir name (`3-in-development`), the short form
(`in-development`), or the display name (`"in review"`).

*State machine* (anything else is rejected):

----
to-do → ready → in-development → in-review → done
                                     ↘ rework → in-review
backward/abort:  in-development → ready,  ready → to-do,  (any non-terminal) → dropped
----

`done` and `dropped` are terminal. Gates enforced before anything is written:

* *Sign-off* — `--reason` is required for every backward move, every
  `→ rework`, and every `→ dropped`; the human running/approving the command
  is the sign-off, and the reason is recorded in History (and the
  DROPPED/REWORK board cell). Forward moves may omit it.
* *Per-child WIP* — moving into `in-development`/`in-review` cannot exceed
  that child's limit (from `pickle.toml`); counts only the ticket's own
  `project`.
* *Dependency + cross-child merge gate* (pickup only) — every `depends-on:`
  target must be `done` *and* carry a `MERGED` History line (the cross-child
  proxy for "merged to its own base"). This is stricter in substance than
  `board audit`: the audit errors on a dependency that is not done and warns
  on one that is done but unmerged, while the pickup gate demands the `MERGED`
  History line outright. *`spawned-by:` takes no part in this gate* — lineage
  is provenance, so a ticket is pickable however its parents stand.
* *Gate table* — the target status's own required sections/`### ` headings
  (see <<cmd-board-audit>>'s gate-table bullet) must already hold in the
  ticket's *current* text: a **blocking** row unmet refuses the move outright,
  before anything is written. An **advisory** row unmet (e.g. `## Outcome`)
  never refuses — `ticket move`'s own post-move `board audit` self-check
  (below) is what reports it, as a warning.

After applying, `ticket move` runs `board audit` as a self-check and fails
loudly if the tree is no longer clean.

A move is a *rename*: it writes the ticket at its new status path and removes
the old one. The printed summary therefore names **both** halves, plus the
regenerated `BOARD.md`, as a ready-to-paste `git add` — the old path is the
one rules §0's explicit-pathspec rule needs but is easy to leave out from
memory, and a bookkeeping commit that stages the add without the delete lands
a duplicate ticket id in git history that a worktree-based `board audit`
cannot see:

----
moved T-081: IN REVIEW → DONE  (tickets/6-done/T-081-example.md)
  removed  tickets/4-in-review/T-081-example.md
  stage:   git add tickets/6-done/T-081-example.md tickets/4-in-review/T-081-example.md tickets/BOARD.md
----

[#cmd-board-audit]
== `pickle board audit`

A pure, dependency-free check of the flow invariants over `tickets/` +
`pickle.toml`. It prints `ERROR:`/`WARNING:` lines plus a summary for every
invariant that fails, but the two severities do not carry equal weight: it
exits non-zero only when at least one *error* fires; a *warning* — including
the unfinalized-merge one below — is a routine, expected nudge (merging is
the human's and may lag) and never changes the exit code:

* each ticket file sits in a known status dir and is named `T-NNN-<slug>.md`;
* frontmatter is complete (`id`, `title`, `project`, `depends-on`,
  `spawned-by`, `impact`, `complexity`, `cost`), with no key repeated — a
  duplicate key silently overwrites at parse time (last value wins), so it is
  flagged wherever it is found; grades are legal, the id matches the filename,
  and ids are unique globally;
* `project:` names a *registered child*, every `depends-on:` target exists
  *and is not the ticket itself* (a self-referencing dependency audits clean
  and then silently self-blocks at pickup, since it can never reach
  `6-done/`), and every `spawned-by:` target exists without a ticket citing
  itself — lineage is checked for existence but *never gates* anything;
* `BOARD.md`'s ticket rows match a fresh render of the ticket files — the
  board is a *generated artifact*, checked in two tiers: if every rendered
  ticket row (its status section, child sub-group, and cell text) still
  matches, but the file's *generated layout* around those rows is out of
  date — the preamble, a per-child WIP-limit line, a `### <child>`
  sub-heading or its `(n/limit)` count, an empty child table, row order —
  that is a *warning*: `BOARD.md is out of date in its generated layout only
  (every ticket row matches) — run pickle board sync`. If any row itself
  disagrees — added, removed, moved to another section or child, or its cell
  text changed — that is an *error*: `BOARD.md does not match the ticket
  files (rows differ) — run pickle board sync`. Both name the same fix; only
  the severity differs, because nothing can tell a hand-edit apart from a
  routine consequence of a registry or renderer change — only whether the
  file still tells the truth about the tickets;
* *per-child* WIP limits (`wip_in_development`/`wip_in_review`) hold;
* each ticket's last History transition matches its directory;
* nothing is in `3-in-development/` with a dependency not yet in `6-done/`
  (warning if a done dependency has no `MERGED` History line) —
  `spawned-by:` parents are deliberately exempt;
* every ticket in `6-done/` carries a `merged to <base>` History line — a
  *warning*, never an error, since a done ticket legitimately sits unmerged
  for as long as the human takes: `DONE but has no 'MERGED' History line —
  not merged yet, or the merge line was forgotten (rules §4: append it and
  run pickle board sync)`. This is the same check as the dependency-scoped
  bullet above, generalized to *every* done ticket rather than only those
  named in some other ticket's `depends-on:` — the common case (nobody
  depends on it) was otherwise never checked. `7-dropped/` is out of scope:
  a dropped ticket has nothing to merge;
* all seven status directories (`1-to-do/` … `7-dropped/`) exist — a missing
  one is an error, since `pickle install` promises all seven on every clone;
  one that exists but is empty and carries no `.gitkeep` is only a *warning*
  (git does not track empty directories, so a fresh clone would lose it next);
* a status-transition or merge History line stays within 400 runes (a
  *warning*): the two forms `tickets/README.md` §1 prescribes
  (`OLD → NEW: reason`, `merged to <base> (<ref>)`) have a shape to violate,
  so an outlier — a paragraph of pipeline detail pasted onto one dated line —
  is flagged and should move into the Description or `tickets/NOTES.md`.
  `created` lines and other free-form dated notes carry no such shape and are
  exempt, however long;
* every status's own **gate table** holds — the sections (and, inside
  `## Implementation Plan`, the `### ` sub-headings) that status requires,
  each row present with a non-empty body. Two severities: a **blocking** row
  unmet is an *error* (`2-ready/` … `5-rework/` require the plan section plus
  its seven READY-gate steps — rules §4 — in order: feature branch,
  prerequisite gate, confirmed decisions, tasks, acceptance test, docs
  update, finish; `5-rework/` additionally requires `## Review`); an
  **advisory** row unmet is only ever a *warning* (`## Outcome`, absent,
  empty, or still the `TEMPLATE.md` placeholder, on every non-terminal
  status — T-083's original check, now one row of this table). `6-done/` and
  `7-dropped/` declare no rows at all, so *this table* never flags a permanent
  archive, however old or incomplete the ticket — the unfinalized-merge
  warning above is a separate check, and it does apply to `6-done/`. The
  check is purely structural (a
  named heading present with a non-empty body once HTML comments are
  stripped) — it proves a step exists, never that its content is *good* —
  and `ticket move` enforces the blocking half of the same table *before*
  writing anything (<<cmd-ticket-move>>), so a ticket already past a gate
  failing here means its plan changed out from under it after the move, not
  that the move let it through.

[NOTE]
====
*Upgrading an existing project:* `spawned-by:` is a *required* key, and
`pickle upgrade` never touches tickets. Tickets written before this key
existed therefore report `frontmatter missing "spawned-by"` until you backfill
them — add `spawned-by: []` under each ticket's `depends-on:` line (a one-line
mechanical edit per file).

The 120-rune cell cap (see <<cmd-board-sync>>) has the same shape, and stays
an *error*, not a warning: a board rendered before the cap existed holds a
cell longer than a fresh render would produce, which is a row disagreeing —
`BOARD.md does not match the ticket files (rows differ)` — until you run
`pickle board sync` once.

The status-directory check has the same upgrade-visible shape too: a project
cloned before its `.gitkeep` files were committed (git does not track empty
directories) now reports a missing-directory *error* — and because `pickle
upgrade` deliberately never writes under `tickets/`, it cannot self-heal this.
Re-run `pickle install` (idempotent; it only creates what is missing) to
restore the directory and its `.gitkeep`, then re-run `pickle upgrade` or
`pickle board audit`.

The gate table's blocking rows have the same upgrade-visible shape a fourth
time. Like the other three it reports an *error*, and every one of the four
therefore makes **`pickle upgrade` and `pickle install` themselves fail**,
not only `board audit`: both run this same post-operation audit self-check
and exit non-zero when it reports an error (the install/upgrade itself
still completes — the self-check's exit code is what reports the pre-existing
violation). What differs here is the *fix*: the other three clear
mechanically — one `pickle board sync`, one re-run of `pickle install`, one
backfilled `spawned-by: []` line — while this one needs a heading written by
hand into each affected ticket's plan. One legacy ticket in `2-ready/` …
`5-rework/` whose Implementation Plan predates the table — missing one of the
seven READY-gate `### ` headings, or the section itself — is enough to turn
an otherwise unrelated upgrade or fresh install into a reported failure. The same is true
of `pickle ticket move`: once one such ticket exists anywhere in the tree,
*every* subsequent move — even of a different, unaffected ticket — reports
"move applied but board audit now reports N error(s)" from its own post-move
self-check (the move itself still lands; nothing rolls back).
**`pickle board sync` will usually *not* surface it** on its own: `sync`
only re-runs the audit self-check when it actually rewrites `BOARD.md` (a row
or the generated layout was stale), and nothing about a ticket's
`## Implementation Plan` body feeds any board column — so a gate-table
violation confined to the plan typically leaves the board itself unchanged,
and `sync` reports "already in sync" with no error at all. Run
`pickle board audit` directly, **before** upgrading, to find every ticket the
migration affects. There is no migration flag and nothing to grandfather:
write the missing heading (it need only say what the ticket's own plan
actually does — even "none" satisfies a Prerequisite gate or Docs update
row). From `2-ready/` specifically, moving the ticket back to `1-to-do/`
(whose only requirement is `## Outcome`) also clears it; from
`3-in-development/`, `4-in-review/` or `5-rework/` no single move does
(brine's transition table gives none of them a legal move to a state without
the same requirement), so writing the heading in place is the only way out.
====

[#cmd-board-sync]
== `pickle board sync`

----
pickle board sync [--dry-run]
----

*Regenerates `BOARD.md` wholesale from ground truth* (ticket files +
frontmatter + `pickle.toml`). The board is a pure generated artifact: the
whole file — banner, preamble, WIP-limit lines, and the seven status
sections — is a render, and *nothing in it is preserved*; hand-written
planning notes belong in `tickets/NOTES.md`, which sync never touches. *"In
sync" is defined as `board audit` reporting zero errors*, so a successful sync
always leaves the board audit-clean.

Everything on the board is derived:

* section per status directory, one `### <child>` sub-group per registered
  child, `(n/limit)` WIP counts computed at render time;
* deterministic ordering — TO DO/READY by descending impact (ties by id),
  everything else by id; every DONE/DROPPED ticket is always listed (nothing
  "ages off");
* DONE `merged` from the ticket's merge History line (`yes — merged to …` /
  `no — publish-gated`), DROPPED `reason` and REWORK `open findings` from the
  last transition's `--reason`;
* every cell passes one-way sanitisation (`|` → `¦`, newlines → space, then a
  120-rune cap with a trailing `…`) — cells are never parsed back, so a pipe in
  a title cannot corrupt the table and an over-long value cannot make a whole
  status table unreadable. The cap is a *rendering* bound: the ticket file keeps
  the full text, and it stays the source of truth. If your board has a longer
  cell from before the cap existed, `board audit` reports it as a row-level
  error (<<cmd-board-audit>>) until you run `pickle board sync` once.

A board differing from a fresh render only in the `Last updated:` date is in
sync — no write. `--dry-run` reports the drift, writes nothing, and *exits
non-zero if the board would change* (wire it into CI). After a write, sync
runs `board audit` as a self-check.

[#cmd-board-state]
== `pickle board state`

----
pickle board state --json
----

*Prints the whole ticket tree as one versioned JSON document* — every
registered child-project, every ticket's frontmatter, parsed `## History` and
dispositioned `## Review` findings, per-child WIP counts and their caps, and
an audit-health summary. Read-only: nothing under `tickets/` is ever written.
Intended for a programmatic consumer (an agent-harness extension, a CI step,
a git hook) that would otherwise have to scrape the other commands' prose or
re-implement the tree walk and grading/WIP/audit rules `internal/board` and
`internal/audit` already own.

`--json` is *mandatory*, not a default: `pickle board state` without it prints
this usage line and exits `2`, writing nothing to stdout. A bare invocation is
therefore a safe thing to type while exploring the CLI, and a future
human-readable default (if one is ever added) is not a breaking change for
anything already scripted against the flag.

The document is a pure function of the tree, `pickle.toml`, and the binary's
own version — running it twice against an unchanged tree produces
byte-identical output (no timestamp field), so it diffs and scripts cleanly.
The whole read runs inside the same shared tree lock `pickle serve` uses (the
lock paragraph at the top of this chapter), so it never observes a concurrent
writer's half-finished change.

=== Envelope and compatibility

[cols="1,3"]
|===
| Field | Meaning

| `schema`
| An integer, bumped only when a field is removed or retyped. *Adding* a field
  is always a compatible change and never bumps it — a consumer should ignore
  fields it does not recognise rather than fail on them.

| `pickle_version`
| The emitting binary's version string.

| `flow`
| The configured flow name (`pickle.toml`'s `flow` key).

| `root`
| The absolute path to the project root this document describes.

| `states`
| Every status the flow defines, in board order — `{name, dir, terminal,
  wip_key}`. Derived from the flow definition, never hardcoded, so a
  consumer never needs to know a status's directory name in advance.

| `children`
| Every registered child-project, in `pickle.toml` order — `{name, wip}`,
  `wip` being one entry per WIP-limited state: `{key, dir, status, count,
  limit}`.

| `tickets`
| Every ticket, flattened into one array in the board's own order (state,
  then child, then the board's own within-child sort) — see below.

| `health`
| `{tickets, errors, warnings, board_drift}` — what `pickle board audit`
  would report right now. `board_drift` is `none`, `layout` or `rows` —
  the same vocabulary `board audit` itself uses for `BOARD.md` freshness —
  or `unknown` when the tree itself failed to load (a structural problem
  reported in `errors`, e.g. a ticket file with no frontmatter block) and
  so cannot be freshly rendered to compare against. `unknown` means "not
  computed", never a fourth drift verdict; check `errors` first.
|===

=== Ticket fields

Each entry in `tickets` carries: `id`, `num`, `prefix` (the child's ticket-id
prefix), `title`, `project`, `status` (display name, e.g. `"IN REVIEW"`),
`dir`, `file` (basename), `slug`, `impact`, `complexity`, `cost`,
`depends_on`, `spawned_by`, `family`, `duplicate_keys` (malformed repeated
frontmatter keys, if any), `front_matter` (the raw frontmatter map, so an
unknown or project-specific key survives), `merged` (the merge `## History`
line, `""` when unmerged), `history` (one `{date, kind, target, text}` per
`## History` entry, `kind` one of `created`/`merged`/`transition`/`note`),
and `review` (below). Every per-ticket path is repo-relative, so the ticket
entries are identical from any checkout location; `root` in the envelope is
the one absolute path in the document, and therefore the one field that
differs between two checkouts of the same tree. Compare with `root` removed
(`jq 'del(.root)'`) if you want byte-identical output across machines.

=== The `review` field, and its one caveat

`review` is `{tables, headers, findings, disposition_summary, cost_line}`.
`findings` carries only the closed-vocabulary columns of a ticket's `##
Review` findings table(s) — `id`, `severity`, `class`, `disposition` — never
the three prose columns (`description`, `evidence`, `suggestion`, under any
of their header spellings). `disposition_summary` and `cost_line` are the
two closer lines beneath the table, copied verbatim and left unparsed.

*This is a best-effort read of hand-written markdown tables*, not a strict
parser for one fixed schema. The review-protocol's canonical seven-column
header (`id | severity | class | disposition | description | evidence |
suggestion`) was fixed only from 2026-08-13 onward and was never backfilled,
so older tickets still use several header shapes. Detection is by column
*name*, not by position: a table counts as a findings table only when its
header has a column named exactly `severity` and one named exactly
`disposition`. If the `class` column is missing, every row reports
`"class": ""` rather than borrowing a value from a neighbouring column.
`headers` exists so a consumer can see which header shape was actually parsed
for a given ticket, instead of trusting the extraction silently.

=== Two worked examples

Find one ticket by id:

----
pickle board state --json | jq '.tickets[] | select(.id == "T-065")'
----

Count non-blocking findings by `class` across every DONE ticket:

----
pickle board state --json \
  | jq -r '[.tickets[] | select(.status == "DONE") | .review.findings[]
            | select(.severity == "non-blocking") | .class] | group_by(.)
            | map({(.[0]): length}) | add'
----

[#cmd-board-decisions]
== `pickle board decisions`

----
pickle board decisions [--project <child>] [--status <dir>] [--grep <regex>] [--json]
----

*Queries every ticket's `### Confirmed design decisions` subsection* and prints
each item already in citable `<ID> decision <N>` form. Read-only: nothing
under `tickets/` is ever written, and the whole read runs inside the same
shared tree lock `pickle serve` and `pickle board state` use. Unlike
`board state`, `--json` is *not* mandatory here — the default output is a
short, human-shaped table, not a full document dump, so a bare invocation is
already the common case.

Every flag is optional and they compose:

[cols="1,3"]
|===
| Flag | Meaning

| `--project <child>`
| Narrow to one registered child-project's tickets. An unregistered name is
  an *error* (exit `1`); a registered child that simply has no matching
  decisions is exit `0` with an empty result — these are different outcomes,
  and the command is deliberate about which is which (see *Exit codes*,
  below).

| `--status <dir>`
| Narrow to one status *directory* (e.g. `6-done`, not the display name
  `DONE`). An unknown directory is an error naming the legal values, read
  from the flow definition rather than hardcoded.

| `--grep <regex>`
| A regular expression, matched case-insensitively against each decision's
  *whole* text — the statement and the rationale that follows it — because a
  topic search needs to reach the rationale even though the output never
  prints it (see below). An uncompilable pattern is an error, not zero
  results. Write `(?-i:…)` inline for a case-sensitive sub-match.

| `--json`
| Print the machine-readable form instead of the table (see below).
|===

A decision is projected, never invented: the ticket id, its own ordinal *as
written in the file* (a gap — `1, 2, 4` — is reported as `4`, never
renumbered, because another ticket may already cite it), and — when the
numbered item opens with a `**bold run**` — that run as the statement, with
emphasis/code markers stripped. An item with no leading bold run is reported
as unstructured, carrying its raw first line instead; the rationale prose is
*never* projected in either case, structured or not (only searched, via
`--grep`).

The text form's columns are `DECISION` (the pasteable `<ID> decision <N>`),
`PROJECT`, `STATUS`, `FORM` (`bold` when a statement was found, `raw`
otherwise) and `STATEMENT` (the projected statement, or the raw first line
for a `raw` row). A closing line always summarises the count, `board
decisions: N decision(s) from M ticket(s)`, so an empty result prints a
clear `0` rather than silence.

The `--json` form is this command's own small envelope, versioned
independently of `pickle board state --json`'s `schema` (T-105 decision 13
— the two evolve on separate schedules): `{schema, pickle_version, filters,
decisions}`, where `filters` echoes back the `--project`/`--status`/`--grep`
values the document was built from and `decisions` is an array of `{ticket_id,
prefix, num, project, status, dir, file, number, citation, structured,
statement, raw}` — always `[]`, never `null`, when nothing matched.

=== Exit codes

An **unregistered** `--project`, an **unknown** `--status` directory, and an
**uncompilable** `--grep` pattern are each an error (exit `1`). A
**registered child with no matching decisions**, or **any filter combination
that simply matches nothing**, is exit `0` with an empty result — these are
legitimate answers, not failures, and the command is deliberate about the
distinction: an ad-hoc `grep`-based script this command replaces routinely
conflated the two by leaking `grep`'s own exit `1` into the empty case.

[#cmd-changelog-check]
== `pickle changelog check`

----
pickle changelog check [--since <ref>] [--until <ref>] [--changelog <path>] [--section <name>] [--show-excluded]
----

A *read-only, advisory* report (T-093): for every ticket that shipped in
`--since`..`--until` (defaults: the last tag *before* `--until` — precisely,
`git describe --tags --abbrev=0 <until>^` — and `HEAD`), is it named in `--changelog` (default
`CHANGELOG.md`), inside the `--section` section (default `Unreleased`)?
Every shipped ticket that section does not name is printed as a candidate,
pointing at its ticket file.

The command checks *mentions only*, and has no exemption mechanism: a ticket
that deliberately gets no entry — because its own file records a confirmed
decision to fold it into another one, say — is printed like any other
candidate. Whether a candidate needs an entry or already carries a recorded
reason not to is the reader's call, which is why the report points at the
ticket file instead of trying to answer it.

*It never gates anything* — not `board audit`, not CI, not `ticket move` —
and **always exits `0`, even when it finds candidates**: a merged ticket with
no entry yet is not an error, because the entry may legitimately be written
any time before the release. Do not wire this into a CI check expecting a
non-zero exit; it would fire on every ordinary in-flight release and be
ignored. Genuine errors remain errors: a `--since` git cannot resolve, an
unreadable `--changelog`, or a `--section` the file does not contain exits
non-zero.

"Shipped" is computed from `git log --format=%s <since>..<until>` — commit
*subjects*, not a ticket's `## History` merge line — kept only when the
subject is a Conventional Commit for the target child-project's own code with
a ticket id in brackets at the *end* of the subject (e.g.
`feat(cli): add board audit (T-2)`), tolerating one trailing GitHub/GitLab
squash-merge annotation first (`(#31)` or `(!31)`) so a squash button that
rewrites the subject to `feat(cli): add board audit (T-2) (#31)` still
classifies correctly. The trailing bracketed token only counts when its
prefix is one this project actually registers (T-097) — a subject ending in
`(RFC-7231)` is never read as a shipped ticket, however id-shaped that token
looks. A `board: …` bookkeeping commit (the
ticket/board-bookkeeping convention) is deliberately **excluded**: filing,
re-grading or moving a ticket never ships code, so counting it would produce
false candidates. Because this exclusion is the check's only defence against
over-reporting, **the command depends on that convention holding**.

By default the exclusion list is a single summary line — a count plus every
ticket id any excluded subject *mentions* (a whole-subject scan, not just the
id right after `board:`, and restricted to the ticket-id prefixes this
project registers — T-097), e.g. `excluded 28 board:
bookkeeping commit(s) mentioning T-042, T-070, T-080, T-081, T-089, T-090,
T-091 (--show-excluded for subjects)`. Full subjects move behind
`--show-excluded`, because printing them all unconditionally made a
release-sized report mostly noise. The whole-subject scan (T-095), rather
than only the id immediately after `board:`, matters because the rules'
`board: T-NNN[, T-MMM …] …` convention is usually honoured in spirit rather
than to the letter: most multi-id `board:` commits in this project's own
history name their extra ids in the verb phrase (`board: T-089 reviewed and
done, T-090 filed, T-070 re-graded`), not the leading comma-list, and a
stricter parser would silently drop them. Restricting the scan to
registered prefixes (T-097) matters just as much: without it, an ordinary
bookkeeping subject mentioning a non-ticket id-shaped token — `SHA-256`,
`UTF-8`, `CVE-2024` — would be reported as though it named a ticket. A
trailing `(+N with no ticket id)` clause counts
a bookkeeping subject that names **no** ticket anywhere — the loudest
possible symptom of a convention drift, so it is never the thing the
summary hides; when *no* excluded subject names an id at all, the line says
so directly instead of naming an empty list. Pass `--show-excluded` to
print every excluded subject in full, exactly as earlier versions of this
command always did; a project that stops following the `board:` convention
still sees a visibly odd summary (a rising count, or unfamiliar ids) rather
than a silent under-report. A subject that mentions a ticket in parentheses
but matches neither convention — typically a revert, e.g.
`Revert "feat(cli): add a thing (T-050)"` — is never silently dropped
either: it prints in its own short "match neither convention" list, always
in full.

An id whose prefix is no longer registered — a child-project removed from
`pickle.toml`, or one whose `ticket_prefix` was renamed — becomes invisible
to every part of this check, in either direction: it is never reported as a
shipped candidate, never counted into an exclusion summary, and never
matched in the changelog body either (T-097). This is a documented limit of
a read-only, advisory command, not a bug: remembering every prefix a
project ever used would need persistent state the flow does not keep, and
the alternative — matching any `[A-Z][A-Z0-9]*-\d+`-shaped token regardless
of registration — is exactly the false-positive bug T-097 fixed (a
`SHA-256` or `RFC-7231` in ordinary prose read as a fabricated ticket id).

`--until <ref>` (default `HEAD`) closes the range, so a past `--section` stays
auditable once later commits have landed on top of it. **The default
`--since` resolves relative to `--until`, not to `HEAD`**: it is the last tag
before `--until` — precisely, `git describe --tags --abbrev=0 <until>^`. This
matters the moment `--until` is given alone — a `HEAD`-relative default would
make `--until v0.5.0` (with no `--since`) describe `HEAD`'s own last tag
rather than `v0.5.0`'s predecessor, and if `v0.5.0` is that last tag the
range collapses to the empty, falsely-passing `v0.5.0..v0.5.0`. Resolving
from `--until` instead makes `--until v0.5.0` alone mean exactly what it
reads as: audit the `0.5.0` release. When `<until>^` does not *exist at
all* — `--until` names the repository's root commit, or a shallow clone has
no parent to name — the default `--since` falls back to describing
`<until>` itself, the same answer this command gave before `--until`
existed; only when *that* also fails to find a tag does it error, naming
`<until>` rather than `<until>^` so the message blames the actual missing
tag instead of the fallback's own missing parent. This fallback is narrower
than "`<until>^` fails to describe": a reachable parent that simply has no
tag before it — a project's first release, tagged — still errors naming
`<until>^`, exactly as it did before this fallback existed, rather than
falling back to `<until>`'s own tag and silently producing that same
empty-range false pass by another route.

Standing on a freshly-tagged `HEAD` with no `--since` or `--section` given is
an easy moment to misread: the range becomes the *previous* release, audited
against `[Unreleased]`, which can read like a false pass rather than the
wrong question. When `--until` resolves to an exact tag and `--section` is
still its default `Unreleased`, the report adds one advisory line right
after the header, e.g. `note: v0.5.0 is at tag v0.5.0 — this range is
release 0.5.0, not [Unreleased]; try --section 0.5.0` (the ref you passed
and the tag it resolved to are named separately, since `--until` need not
be the tag's own name, e.g. `--until main`). Passing a `--section` other
than the default `Unreleased` suppresses it — an explicit section already
answers "which release am I auditing"; an explicit `--section Unreleased`
is indistinguishable from the default and still gets the note. The note
never changes the exit code.

The check is one direction only: *shipped but unmentioned*. It never reports
the reverse (mentioned but not shipped in this range) — an entry may
legitimately reference an older, already-released ticket for context, and
flagging that would be noise.

This command is the mechanical half of a broader convention — see
<<releasing>> for the other half (`RELEASING.md`, the prose an agent follows)
and the fallback when either file is missing.

[#cmd-serve]
== `pickle serve`

----
pickle serve [--addr|-a host:port]
----

Starts a *local, read-only* web view of the {flow} flow and runs until you stop
it with kbd:[Ctrl+C]. Default address `127.0.0.1:8745`; `--addr` (`-a`)
overrides it.

*It never writes.* No route creates, moves, rewrites or regenerates anything —
not even a stale `BOARD.md`. `pickle ticket new`, `pickle ticket move` and
`pickle board sync` remain the only writers, so it is safe to leave the server
running while you or an agent work on tickets — every read it does takes only
a shared lock on the ticket tree, which never excludes another reader and
never blocks behind a write for long (writes are quick, whole-tree
operations, not held open).

What it serves:

[cols="2,3"]
|===
| Path | Page

| `/`
| The board. The four active statuses — READY, IN DEVELOPMENT, IN REVIEW, REWORK —
  render as side-by-side columns, one row of columns per registered
  child-project; TO DO, DONE and DROPPED keep the stacked, full-width layout
  below them. Every group, column or stacked alike, is still ordered in
  exactly the order `BOARD.md` uses (impact descending, ties by id) — every
  view calls the same ordering code, so none of them can disagree. A filter
  bar narrows the board to a single child-project (or `All`), and a search box
  narrows it further to tickets whose id or title matches what you type; both
  selections survive the five-second refresh.

| `/t/T-NNN`
| One ticket: frontmatter as fields, the body rendered as Markdown, and *both*
  directions of its edges — `depends-on`/`spawned-by` as written, plus the
  reverse `blocks`/`spawned` edges, which no single ticket file records.

| `/activity`
| Every dated `## History` line in the project, merged and newest-first — what
  moved, when, and why. The board shows current state; this shows movement.

| `/healthz`
| `ok`, for scripts.
|===

Every request re-reads the ticket files, so a reload always shows the tree as it
is now; the board and activity views additionally refresh themselves every five
seconds, which makes the dashboard usable as an ambient window while tickets move.

The dashboard follows your operating system's light/dark preference
automatically. There is deliberately no toggle: a read-only server that stores
nothing has nowhere to remember your choice. Note that a browser with no
expressed preference reports _light_ — `no-preference` was dropped from Media
Queries L5 — so the dark palette is the fallback only where
`prefers-color-scheme` is unsupported.

A banner on every page reports what `pickle board audit` would say right now —
including a stale board — plus each child's WIP counts against its limits. It
*reports*; it never repairs. Fix findings with `pickle board sync` or by editing
the ticket.

The startup line also names the resolved <<install-layout,layout>>. In the
`in-tree` layout, a second banner appears when the checked-out branch looks
like a feature branch (it matches a registered child's `branch_prefix`, or
`HEAD` is detached) — the one situation in which this page can be showing a
ticket status behind the base branch, since bookkeeping only ever lands
there. The banner names the branch and lives outside the polled board
fragment, so it never flickers on the five-second refresh. It never appears
under the `umbrella` layout: no board in that layout can be forked by a code
branch in the first place. `serve` never guesses which branch is the *base* —
it checks the shape of a *feature* branch instead, which every registered
child already names.

[WARNING]
====
The dashboard has *no authentication*. The default address is loopback-only for
that reason. `--addr` accepts any address, and a non-loopback one prints a
warning: anyone who can reach the port can read every ticket in the project. Do
not expose it.
====

[#cmd-scaffold-docs]
== `pickle scaffold docs`

----
pickle scaffold docs [--project-name <name>] [--force] [--dry-run]
----

An entirely optional, standalone scaffold, unrelated to {flow}: `pickle install`
continues to lay down only the ticket flow (`tickets/`, `BOARD.md`, the skill,
the `AGENTS.md`/`CLAUDE.md` markers); this command touches none of that, reads
and writes no `pickle.toml`, and is never checked by `pickle doctor` or
`pickle board audit` — it is a one-shot scaffold, not an ongoing invariant
pickle owns.

It writes, into the current directory:

[cols="2,3"]
|===
| Path | What

| `docs/attributes.adoc`
| Minimal AsciiDoc shared attributes (`:product: <project-name>`).

| `docs/user-manual.adoc`
| A book master including `attributes.adoc` and one placeholder chapter.

| `docs/user-manual/introduction.adoc`
| One placeholder chapter, marked `TODO` — a starting point, not content.

| `.github/workflows/docs-release.yml`
| A standalone GitHub Action, triggered on `release: types: [published]`
  (decoupled from any particular release tool), that builds the manual with
  `snowball` and attaches the PDF/EPUB to the release. GitHub-only — it uses
  `gh` and the `release` event, both GitHub-specific; the file says so in its
  own header comment.
|===

`--project-name` (default: the current directory's name) is substituted for
every `<project-name>` above. `--force` overwrites files that already exist
(without it, an existing file is left untouched and reported as skipped).
`--dry-run` prints what would be created or changed without writing anything.

Two more things happen, best-effort:

- If a `justfile` already exists, `docs-check`/`docs-build` recipes
  (`snowball check` / `snowball build -o dist/docs`) are appended for whichever
  of the two is not already defined. No `justfile` is ever created from
  scratch — a repo with no task runner does not get one invented for it.
- If the `snowball` binary is on `PATH`, `snowball init` is run to write a
  starter `snowball.yaml`; pickle never hand-writes or edits that file. A
  missing or failing `snowball` is reported as a note, never a failure —
  either way, the command prints a reminder to point `snowball.yaml`'s `src`/
  `out` at the scaffolded manual.

[#cmd-version]
== `pickle version` and `pickle help`

`pickle version` prints the build version: the value stamped at build time
(goreleaser / `just build`), falling back to the module version the Go
toolchain records (so a `go install …@vX.Y.Z` binary reports its tag), and
`dev` only when neither exists. `pickle help` (exit `0`) and a bare `pickle` with
no arguments (exit `2`) both print the full usage summary. An **unrecognised**
command is terser — one line naming `pickle help`, exit `2` — so an older
`pickle` left first on `PATH` degrading on the once-unknown `hooks` verb
(<<cmd-hooks>>) does not bury the guard's own one-line notice under a full
usage dump on every commit.
