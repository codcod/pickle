[#project-structure]
= Project Structure

What an instrumented project looks like on disk, and what belongs in git. The
authoritative list of what `install` writes is <<cmd-install>>; this page is
the map around it.

== The workspace after install

The *overarching project* is the directory holding `pickle.toml` — one board,
one ticket-id namespace. Under it sit the *child-projects*, the actual build
targets (see <<multi-project>>):

----
my-app/                           ← overarching project — pickle.toml lives here
├── pickle.toml                   ← child registry + pinned payload version
├── AGENTS.md                     ← agent instructions; holds the pickle marker block
├── CLAUDE.md                     ← --agent claude: marker block, or symlink to AGENTS.md
├── opencode.jsonc                ← --agent opencode: reviewer subagent + bash guardrails
├── .agents/
│   └── skills/
│       └── brine/                ← the skill payload — SKILL.md + resources/
├── .claude/
│   └── skills/
│       └── brine                 ← --agent claude: symlink to the payload above
├── .pi/
│   └── extensions/               ← --agent pi: pickle-guardrails.ts, docs-readability.ts
├── tickets/
│   ├── README.md                 ← pointer to the skill
│   ├── BOARD.md                  ← the generated index
│   ├── NOTES.md                  ← hand-written planning prose
│   ├── 1-to-do/                  ← the seven status dirs, flat, each with a .gitkeep
│   ├── …
│   └── 7-dropped/
├── frontend/                     ← a registered child-project — its own git repo
└── backend/                      ← another
----

Only `pickle.toml`, `AGENTS.md`, `{skill-dir}/` and `tickets/`
are unconditional; the rest depend on `--agent` and on how many children you
register.

== Three kinds of file

pickle-owned::
  `{skill-dir}/`, the `.claude` symlink, the `.pi` scaffolds,
  and the `<!-- pickle:begin -->`…`<!-- pickle:end -->` region inside
  `AGENTS.md`/`CLAUDE.md`. Both `pickle install` and `pickle upgrade` replace
  `{skill-dir}/` wholesale (<<skill-dir-labels>>), pruning anything the
  payload does not ship, and re-inject the marker region whole; the `.claude`
  symlink and `.pi` scaffolds are refreshed individually instead. Keep
  hand-written notes *outside* all of them (above the markers, in
  `AGENTS.md`'s case).

tool-managed, still yours::
  `pickle.toml` — hand-edits survive every load, though `project add|remove`
  re-render it and drop comments (see <<configuration>>). `opencode.jsonc` is
  written once and is yours from then on.

instance data::
  everything under `tickets/`. No command ever rewrites a ticket body;
  `BOARD.md` is the one generated file among them, and `NOTES.md` is never
  touched.

== What to commit

*Everything `pickle install` writes is meant to be tracked.* It produces no
build artifacts, so a project using the in-tree layout (`--in-tree`,
`path = "."` — see <<install-layout>>) has nothing to add to `.gitignore` on
pickle's account. A *second* child
registered at a nested path is different. It is another repository's working
tree sitting inside this one, and until `.gitignore` ignores it, it is an
ordinary stageable directory like any other. `pickle project add` and
`pickle doctor` both say so (see <<cli-reference>>), but pickle never edits
`.gitignore` itself.

[cols="2,3"]
|===
| Path | Why it is tracked

| `pickle.toml`
| The child registry, the commit policy, and the payload version this project
  is pinned to.

| `AGENTS.md` (and `CLAUDE.md`)
| The instructions every agent reads. The marker block is regenerated, but it
  is regenerated *into a file you own* — commit it so a fresh clone briefs the
  agent identically.

| `{skill-dir}/`
| Real files, not a fetched dependency. Committing them pins the exact rules
  in force, and turns `pickle upgrade` into a reviewable diff.

| `.claude/skills/brine`
| Git tracks symlinks; without it the Claude wiring is missing on a clone.

| `.pi/extensions/*.ts`, `opencode.jsonc`
| The per-agent guardrails — the publish gate and explicit-pathspec staging
  only bind if they are present.

| `tickets/**`
| The record of why every change was made: descriptions, plans, review
  findings, History.

| `tickets/*/.gitkeep`
| Git does not track empty directories; these keep the seven statuses present
  on a fresh clone.

| `tickets/BOARD.md`
| Generated — and committed anyway, see below.

| `CHANGELOG.md`, `RELEASING.md`
| Optional and project-authored — pickle never writes either, so if you keep
  them, they are yours to track. Committing them is what lets
  <<cmd-changelog-check>> and the <<releasing>> convention read the same
  release procedure everyone else on the project sees.
|===

=== The board: generated, and still committed

It is the first thing anyone opens, so it has to exist in a clone. And
committing it is what makes `pickle board sync --dry-run` a useful CI check:
it exits non-zero when the tracked board differs from a fresh render, catching
a ticket move whose board regeneration never got staged.

Never hand-resolve a `BOARD.md` merge conflict. Take either side and
regenerate:

[source,sh]
----
git checkout --ours tickets/BOARD.md && pickle board sync
----

A commit that only changes ticket/board state (a ticket file, `BOARD.md`) uses its own compact
form instead of Conventional Commits — `board: T-NNN <verb phrase>` — since a ticket-state
change isn't a product change; see the brine skill's `tickets-README.md` §0 for the exact
grammar. This applies to every project, with any number of children, not only the single-repo
case below.

== The root child — one repo in both roles

The in-tree layout (<<install-layout>>) is the shape where the overarching
project and its sole child are the same repository. `--in-tree` registers
that child itself, at `.`, naming a project only when you want one other than
the root directory's own name:

[source,sh]
----
pickle install --in-tree --project backend
----

This is the *degenerate case of the multi-project model*, not a separate
mode: once `layout` is recorded, `pickle doctor` (<<cmd-doctor>>) checks that
it agrees with the registered children, but nothing else about ticket/board
mechanics differs by path — the child path simply resolves to the root, so
the overarching project and its sole child are the same directory and the
same git repository.

What that changes in practice:

* `pickle doctor` checks that every registered child is a git repo, so a child
  at `.` requires a `.git` at the root — install into the repository itself,
  not into a parent directory holding it.
* One history carries both roles, so the split between them has to be
  deliberate. `tickets/`, `BOARD.md` and `pickle.toml` sit in the same repo as
  the `feat/T-NNN-<slug>` branches cut from it: code belongs on the feature
  branch, while **ticket and board bookkeeping belongs on the base branch**.
  Bookkeeping that rides along on a feature branch is folded into one commit —
  or dropped — by a squash-merge, and the board then indexes tickets whose
  recorded status disagrees with where the files actually are.
* Nothing about `git add tickets` *looks* wrong on a feature branch, which is
  why `pickle hooks install` exists: it installs a `pre-commit` hook that
  refuses staged `tickets/` paths while a feature branch is checked out, and a
  `pre-push` hook that catches the same bookkeeping at publish time — the
  range against the remote base carried by a push whose *destination* is such
  a branch — the one moment `pre-commit` structurally cannot see. Hooks are per-clone (see
  <<cmd-hooks>>).
* Commit hygiene therefore matters more, not less: stage with explicit
  pathspecs (`git add <paths>`, never `git add -A`) so a code commit does not
  sweep up an unrelated board regeneration, and keep ticket/board bookkeeping
  in its own commit.
* The publish gate still applies. With `child_publish_gated` left at its
  default, the agent commits locally but does not push without your
  approval — and because there is only one repo, that gate covers the
  bookkeeping commits too.
* Merging the child's feature branch defaults to **preserving commits**
  (rebase or keep-history) rather than squashing. Here, squashing would
  flatten the product's own `feat`/`fix`/`ci` structure into one commit
  sharing a log with bookkeeping. The Finish step tidies WIP commits into a
  small number of atomic ones before presenting them for approval.

Adding a second child later needs no rework: `pickle project add <name>
<path>` registers it, the root child stays exactly as it is, and the board
grows a sub-group.

=== What choosing in-tree costs

Keeping bookkeeping on the base branch is the rule that makes the layout work,
but it is not free. Four consequences follow from it, and none of them is a
bug to be fixed — they are the price of having tickets live in the code
repository, worth knowing before you choose it.

*Every command that reads tickets reports the checked-out branch's copy.*
This is stated for `pickle serve` in <<install-layout>>, but it is not
specific to `serve`: `pickle board audit` and `pickle board state --json` read
`tickets/` the same way. On a feature branch cut last week, all three describe
the board as it stood last week.

*A stale worktree can never show `DONE` for a ticket that is not — but it can
show other statuses out of order.* `DONE` is a terminal status with no move
back out of it, so a worktree that lags the base branch may show a ticket as
`IN DEVELOPMENT` when it is really `DONE`, but never the reverse. That half is
a reassuring property and a hazard at once: nothing ever looks alarming
enough to investigate, so the wrong answer is easy to accept and act on. It is
not the whole picture, though — a ticket can also move *backward*
(`in review` sent to `rework`, `ready` dropped), and there a stale worktree
shows the **earlier**, further-along-looking status instead of the
correction: over-reporting, not under. Either way, when a status reads
different from what you expected, check which branch you are on before you
conclude the board is wrong.

*CI fires on every bookkeeping push.* Bookkeeping lands on the base branch, so
a workflow triggered by pushes to that branch runs once per bookkeeping
commit — a full pipeline for a change that touched one markdown file and no
code. A run of ticket moves can therefore cost several CI runs for zero
product change. The mitigation is a `paths-ignore` entry for the ticket tree:

[source,yaml]
----
on:
  push:
    branches: [main]
    paths-ignore:
      - 'tickets/**'
----

Prefer `paths-ignore` over `paths`, so a new top-level directory is covered by
CI by default rather than silently skipped.

*The base branch's history interleaves board moves with code.* `git log` on
the base branch alternates between `feat:`/`fix:` commits and `board:` ones.
The distinct `board:` prefix exists partly for this reason: it makes the
bookkeeping filterable, so changelog and release tooling can exclude it
(`git log --invert-grep --grep '^board:'`, or a path exclusion such as `git
log -- . ':(exclude)tickets'`). Tooling that does *not* filter will list
ticket moves among the release's changes.
