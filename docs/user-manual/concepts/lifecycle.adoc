[#lifecycle]
= Lifecycle

This section covers the seven statuses, the gates between them, and what a review does. It
summarises §2, §4, §5 and §8 of the skill's rules.

== The seven statuses

[cols="1,1,3"]
|===
| Directory | Status | Meaning

| `1-to-do/` | TO DO | An idea captured; unrefined.
| `2-ready/` | READY | Refined; the Implementation Plan satisfies the READY gate.
| `3-in-development/` | IN DEVELOPMENT | Being built on a `feat/T-NNN-<slug>` branch in the target child's repo.
| `4-in-review/` | IN REVIEW | Built, acceptance test green; awaiting the review protocol.
| `5-rework/` | REWORK | Review found blocking findings; back for a scoped fix.
| `6-done/` | DONE | Built, reviewed, all blocking findings resolved. Terminal.
| `7-dropped/` | DROPPED | Abandoned or obsoleted, kept with a reason. Terminal.
|===

== The state machine

----
to-do → ready → in-development → in-review → done
                                     ↘ rework → in-review
backward/abort:  in-development → ready,  ready → to-do,  (any non-terminal) → dropped
----

`pickle ticket move` enforces this state machine; any other move is rejected. Backward and
abort moves always need a `--reason`. Dropping a ticket from development, review, or rework
also needs explicit user sign-off.

== The READY gate

"Refined" is objective. A ticket is READY only when its Implementation Plan is
a complete, self-contained prompt (§4):

1. *Feature branch* named, cut inside the target child's repo.
2. *Prerequisite gate* stated (or "none").
3. *Confirmed design decisions* the implementer must honour. Each is a numbered item whose
   leading bold run is the decision statement, cited elsewhere as `<ID> decision <N>`;
   the ordinals are never renumbered.
4. *Tasks* — concrete, with exact paths in the target child.
5. *Acceptance test* — runnable commands + expected results, re-runnable
   verbatim.
6. *Docs update* — which docs, or "no user-facing surface".
7. *Finish* — summary + a suggested Conventional Commit message (ticket id in
   brackets at the end of the subject). For a root-path child, WIP commits are first tidied into
   atomic ones. The merge then defaults to preserving them (rebase/keep-history) rather than
   squashing — see <<project-structure>>.

All seven are *mechanically checked*. Each must appear as a required `### `
heading inside `## Implementation Plan`, with a non-empty body. `pickle
ticket move <T-NNN> ready` refuses the move when one is missing, and `pickle
board audit` errors on a ticket already sitting past READY with one still
missing. The rule does not apply in `1-to-do/`: from `2-ready/`, moving a ticket back
there always clears the gate, whatever state the plan is in. It also does not apply in
`6-done/` or `7-dropped/`, which require nothing at all. The unfinalized-merge warning under
*Done ≠ merged* is a separate check, and it still applies to `6-done/`. The check is structural
only: it proves a step is present, never that it says something *good*. Judging whether the
plan's content actually holds up is still the reviewing agent's job.

== Pickup gates

Before a READY ticket enters development, three checks run:

* *Dependencies* — every `depends-on:` target is done *and merged* to the base
  of its own child's repo (see <<tickets>>).
* *WIP limits* — per child: `3-in-development/` ≤ 1 and `4-in-review/` ≤ 1 by
  default (tunable in `pickle.toml`). Exceeding a limit is a rule violation,
  not a judgement call.
* *Applicability* — a freshness re-check of the plan's assumptions against the
  current tree, run on every pickup; a stale plan is routed back to be
  re-refined rather than implemented (§8).

== Reviews: severity, then disposition

A review gives every finding a *severity*:

* *Blocking* — breaks the golden path, ships wrong behaviour, or contradicts a
  locked decision. The ticket moves to `5-rework/`; only the listed findings
  are fixed, on the same branch, then a *scoped* re-review verifies them — and
  reads the diff that closed them, since a fix's own replacement text is the one
  part of the branch nothing has audited yet. The fix pass records the commits it
  made in the ticket's `## Review` so that diff is unambiguous; the review
  protocol's step 1 states the mechanics.
* *Non-blocking* — the ticket proceeds to `6-done/`, and each finding takes
  exactly one of four *dispositions*, recorded in the ticket's `## Review`
  table:

[cols="1,3"]
|===
| Disposition | When

| *fixed inline* | Prose or idiom this branch authored or made false — and no
  behaviour change. Recorded, never a silent edit.
| *folded* | An existing ticket already owns the ground; add or cite an item
  there.
| *new ticket* | It would *actually be scheduled*. Batched by theme — never
  one ticket per finding — with `spawned-by:` naming the reviewed ticket.
| *noted* | None of the above: recorded with its evidence and closed.
  *This is the default.*
|===

The same four dispositions apply at every gate that can spawn a ticket — the
pickup applicability gate and refinement splits use the same vocabulary and
the same default (§5).

Every finding also carries a *class* — one word from a closed vocabulary that names
what *kind* of defect it was. It is orthogonal to severity and disposition and is recorded
in the same table. Blocking findings carry one too: they take no disposition, but the
kind-of-defect axis matters most on them. The vocabulary and the table's canonical column
skeleton are defined once, in the skill's `resources/review-protocol.md` §5, so paste the
skeleton rather than restating the columns. The point is aggregation: severity and
disposition say how a finding was handled, while class says what kept going wrong. A
recurring class is a specification for a `pickle board audit` check.

A review closes with two one-line summaries under the table: the *disposition
summary*, counting each disposition and naming the ids involved, and a
`cost: estimated <S|M|L|XL>, actual <S|M|L|XL>` line. The estimate is copied
verbatim from the ticket's `cost:` frontmatter, which is *not* rewritten — the
divergence between estimate and actual is the datum, and overwriting the
estimate would erase it.

A review also reconciles the project's own governing documents — its design
of record, conventions, the locked-decisions guide, decisions log — against
what the branch shipped, or records explicitly why not. A governing document
the branch made false is classed `stale-xref` and handled like any other
finding; the step adds no severity rule of its own. Within the review's
reach it is reconciled there and then and the edit recorded; out of reach, the
reach limit is recorded as the reason. See the skill's
`resources/review-protocol.md` step 7 for the full rule.

A blocking finding discovered only after a review already moved the ticket to
`6-done/` — while updating references, sweeping dependent tickets, or writing
the summary — has no route back into that ticket, since the status is
terminal; it is filed as its own ticket instead (not the `new ticket`
disposition, since a blocking finding is never dispositioned), `spawned-by:`
the concluded one, with a `## History` line on the concluded ticket recording
the filed id. See the skill's `resources/review-protocol.md` step 6c for the
full rule.

=== Review addenda

Two optional layers can be added on top of the skill's generic review protocol, applied *on
top of — never instead of* it, in this order: the generic protocol, then an **overarching**
addendum (`review_addendum` at the top of `pickle.toml`, true of the whole project), then a
**per-child** addendum (`review_addendum` inside that child's `[[project]]` entry, that
child's tech-specific checks) — see <<configuration>>. An addendum is written as numbered
*additions* keyed to the generic protocol's own step numbers (`Step 2 — Implementation audit
(additions)`), not a parallel checklist a reviewer runs separately.

Adding one is optional, and in practice happens *after* a project has accumulated
project-specific rules a generic reviewer would not know to check — distilled from real review
findings or an audit, rather than written speculatively before any exist. A single-child
project usually has nothing left for the overarching slot to say that the per-child slot
doesn't already say, and should use only the per-child slot.

An addendum's own shape, by convention: a short preamble naming what commit/date it was
written against and restating that it layers on top of the protocol rather than replacing it; a
body organized by the protocol's step numbers, with each item marked **Blocking** or *Advisory*
using this page's own severity vocabulary; a closing revision history, dated like a ticket's
`## History`. It documents the *audit procedure* for a project's existing conventions — its
`AGENTS.md`, its design of record — not the conventions themselves: restating a rule in a
second place is a second place for it to go stale.

Setting `review_addendum` wires the mechanism, but it changes nothing about `AGENTS.md`: unlike
`ticket_prefix`, `branch_prefix`, the WIP limits and the commit policy, it is never rendered
into the marker block by `pickle upgrade` (<<configuration>>). If a project wants a reviewer to
actually find it, it names the addendum file by hand among its other governing documents — a
single pointer (what it's wired as, whether an overarching layer exists), not a restatement of
its content, and stated once rather than repeated across sections.

== Done ≠ merged

DONE records the review verdict. *Merging is always the human's* and may lag —
a dependency counts as satisfied only once its code is actually on the base a
new branch would fork from. When you merge, append a dated
`merged to <base> (<MR ref>)` History line to the done ticket and run
`pickle board sync`. Forget it and `pickle board audit` says so: every ticket
in `6-done/` without such a line draws a *warning* (never an error — the lag
is legitimate, so the audit cannot tell "not merged yet" from "merge line
forgotten"). Add a commit reference alongside the MR ref (a short SHA, and a full
commit link where the remote resolves to a known hosting URL) so the line traces straight to
what shipped. Keep the short SHA even when you add the link: the board's `merged` cell is
capped at 120 runes, which a full commit URL can exceed, so the SHA is what still reads there
— the ticket file keeps the whole line, and `pickle serve` renders it in full, as a clickable
link.
